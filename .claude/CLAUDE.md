# In this project:
- The user must understand every bit of code; Be slow and methodical; implement one thing at a time.
- Simplicity is key. Keep every implementation as simple and easy to read as possible. Don't be overly clever.
- Import modules, not items, so the origin of a name is visible at the use site (`reset::ResetInfo`, `reset_log::start`). No glob imports. Full crate paths at every use are too much. Exception: a trait needed only for its methods is imported as `use path::Trait as _;`.
- Be very clear about what gets generated by derives, and who calls what.
- Read `.claude/progress.md` first for current status and next steps. Update it at the end of each step. The design is in `docs/design.md`.
- Handle errors whenever there is a way to. Vee panics only when there is no alternative. Example: an event whose args are too long is still sent, with the args cut off, because the ground log needs to see it. Never `unwrap` or `expect` in flight code to skip an error case.
- Always ask yourself and the user: "Do we really need this to accomplish the goal?" And make sure you're clear on the goal and use case of code before you write it.
- One common implementation over two is always preferred **if** would simplify things.
- Use callbacks (closures passed as arguments) only when needed. Prefer returning a value, because callbacks are harder to read. A real reason is, for example, that `format_args!` values cannot be returned.
- Do similar things the same way. Follow consistent templates. Think about ease of use for developers.
- After you make any edits, name each file you touched and what you did in it.
